# Mario Kart World GPU stall: offline analysis (2026-11-10)

Scope: the stall that stops the GPU about 40 s after Mario Kart World (`0400C3F00006E000`) loads on `v2`. No boot, no build and no code change was made. Inputs: the game's pipeline cache pulled read-only from the console, the two saved sessions, the `v2` tree at `7e115e3`, PS5_Mesa at `7b59ef27` and upstream `dj-nx2`.

Everything under "Verified" was read in a file or a log and carries its location. Everything under "Inferred" is reasoning on top of that and is marked as such.

## 1. Result

| Rank | Cause | Status | Confidence as the cause of the stalls |
|---|---|---|---|
| 1 | A task program that culls all 32 threads never writes its mesh workgroup count; the epilogue launches whatever the payload word holds. In RADV's emulation that word lives in a 64 MiB ring that is never zeroed and is shared by all task pipelines | defect verified in `v2`, in the baseline and upstream before `8e87cf5a66`; MKW's task programs take the path | about 55% |
| 2 | Something first executed in the same 80 ms as the stop in both sessions: compute `12c5e44ec761705b` (cache record 174) or mesh pipelines `6a9f7874648dd6f6` (records 175 and 176) | association verified, mechanism unknown: no loop in either program, counts not logged | about 30% |
| 3 | Other: a driver-side wait in the mesh emulation, or guest data missing on `v2` | no evidence found offline | about 15% |
| - | Native tessellation or geometry stages (rank 3 of the earlier findings) | eliminated: the game's cache holds no tessellation or geometry stage | - |

The two sessions do not show the same behaviour (section 5). The rank 1 defect explains the first session completely and must be fixed in any case; whether it also explains the second one is what the diagnostic boot settles.

## 4. Question 2: claim B, the unwritten mesh workgroup count

### Verified

`TaskEpilogue` (`Eglantine/src/shader_recompiler/backend/spirv/emit_spirv_mesh.cpp:110-118`) loads payload word 1 and uses it as the X count of `OpEmitMeshTasksEXT`. `EmitMeshPrologue` (`:209-217`) initialises only the mesh primitive count and returns at once for a task program. Nothing clamps the count. The file is unchanged since `f16a241` (EglantinePS5 patch 0004), so the baseline has the same code.

Upstream fixed it in `8e87cf5a66bb8c2d5b48f6ca4e73e030d9101dfc` (SethRamey, 2026-11-06, "vulkan: intel arc fixes for MKW"): the prologue stores zero to payload word 1 for task programs. Its own comment: "A task that culls all its threads never writes the mesh workgroup count, and the payload starts undefined. Intel's garbage there launches enough workgroups to lose the device." Upstream has no clamp either.

MKW's task programs take that path. Record 167 (`dis-r0167-task.txt`):

```
0x0050 ISBE RD.ATTR.32.SKEW R4,[RZ+0]     workgroup index
0x0098 ISETP GE.U P0, R4, c4[0x0]
0x00a8 @P0 EXIT                           index >= count
...    LDG through c0[0x670], FSETP culling against c3[0x100..0x10c]
0x01e8 @!P0 EXIT                          culled
...    VOTE, POPC compaction, payload writes at [R1+0x10..0x34]
0x03d8 @P0 EXIT                           not the highest surviving thread
0x03e8 POPC R0, R221
0x03f0 ISBE WR.ATTR.32.O R0,[RZ+0x4]      the only write of the count
```

When all 32 threads leave at `0x00a8` or `0x01e8`, word 1 is never written. Records 168-171 are the same program with another cascade index, 178-182 are byte-identical to 167-171. Record 99's task has an exit at `0x16d0` before its count write at `0x1da8`. Record 91's task always writes the count.

What RADV then runs (PS5_Mesa `7b59ef27`, the pin of both the baseline and `v2`):

- Task shaders are emulated (`src/amd/vulkan/radv_physical_device.c:72-76`): a compute dispatch, a records prepass, then an indirect draw of the mesh workgroups (`src/amd/vulkan/radv_cmd_buffer.c:15400-15599`).
- The payload lives in a ring inside `device->task_emu_bo`. That buffer is created without `RADEON_FLAG_ZERO_VRAM` (`src/amd/vulkan/radv_device.c:1730-1733`), and "Direct memory arrives with whatever the pool held" (`src/amd/vulkan/winsys/ps5/radv_ps5_bo.c:85-93`). The mesh publish ring a few lines above does ask for zeroes.
- Every task draw starts at ring entry 0 (`radv_cmd_buffer.c:15502`), with a stride of the pipeline's payload size: 256 bytes for records 91 and 99, 1,408 bytes for family B. All task pipelines write over the same bytes.
- No clamp exists on the way: payload loads go straight to the ring (`src/amd/common/nir/ac_nir_lower_taskmesh_io_to_mem.c:189-287`) and the draw record is `x*y*z*parts` in 32 bits (`src/amd/vulkan/nir/radv_meta_nir.c:1438-1458`). The prepass sums assume the application respects `maxMeshWorkGroupTotalCount` (4,194,304; `radv_physical_device.c:2280-2298`).

So the count is byte 4 of that task workgroup's ring entry: the value an earlier draw left there, or the memory the pool handed out. It can be any 32-bit value.

### Inferred

- An entry a survivor of family B wrote earlier holds at most 32. An entry never written holds pool memory, the same value every frame.
- With the two strides, family B's count word of an odd entry falls on payload word 33 of an entry of records 91 or 99. If those pipelines ever draw more than one group, float payload data becomes a count of about 10^9. The log shows `groups=1` for them, but only the first eight mesh draws are logged (`vk_rasterizer.cpp:715`).
- The Vulkan device is created per game (`...132916-eden_log.txt:34` and `:4042`). In session 1 the ring was allocated from a pool Pokopia had used for 20 minutes.

## 5. Question 3: claims C and D, and the two sessions

### Verified

Claim C is true, with one correction.

- `RasterizerVulkan::Draw` (`Eglantine/src/video_core/renderer_vulkan/vk_rasterizer.cpp:586-597`) skips direct draws whose `first + count` passes 2^24. It covers mesh draws too. Instance counts are not checked.
- The mesh path (`:713-728`) calls `DrawMeshTasksEXT(groups, 1, 1)` with the draw's vertex count, ignores the instance count and the draw's `first`, and does not compare `groups` with the device limit (65,535).
- Indirect mesh draws are skipped with a warning (`:770`); that line is in neither log, so MKW's mesh draws are direct. Other indirect draws are unguarded.
- Correction: a direct compute dispatch is already dropped, silently, when a grid dimension passes the device limit (`:1133-1137`). `DispatchIndirect` is unguarded.

Claim D does not hold as stated.

- The baseline has the same defect: same emitter (section 4), same mesh draw code, same Mesa pin.
- The baseline was never booted with MKW on this console: the Results table of `agents/console-test.md:52-56` is empty. "23 to 26 fps" is upstream's measurement on their console (`docs/MKW-BENCHMARK.md:42-49`), four runs that ended at 170 to 221 s, two of them with "device lost".
- Family B's task programs use low guest registers and ordinary instructions; none of the `v2`-only lowering work (register shadowing, tessellation, geometry returns) is needed to accept them.
- The IADD3 immediate fix that went into `v2` after the sessions (`92aa77c`) does not touch MKW: no cached program holds the affected pattern (a scan of all 191 records for `MOV32I R251, <negative>` followed by the negating add found none).

No address link to the 1,453 MiB unmapped region or the skipped sparse maps: the storage pointers visible in the cache (`0x2242a1b000`, `0x21fdb86000` to `0x21ff60edc0`) and the five sparse images (`0x860b4b0000` to `0x8675eb0000`) are outside `[0x859afb0000, 0x85f5faffff]`. The task programs read through `c0[0x670]` and `c0[0x680]`, whose values are not in the cache. Unbound sparse ranges map a shared zero block in this driver (`src/amd/vulkan/winsys/ps5/radv_ps5_platform.c:529-542`), so sampling them does not fault.

The two sessions differ:

| | Session 1 (second game) | Session 2 (first game) |
|---|---|---|
| Family B first drawn | 1256.69 | 148.797 |
| GPU after that | saturated at once: one 7.9 s frame, then about 5.3 s per frame for 66 s (`...132916-stderr.log:875`, `903-923`: `agc_ms` equal to the whole 10 s window) | normal for 1.5 s (`...140333-stderr.log:126`: 5,378 submissions, `agc_ms=146.5`) |
| Compute 174 and mesh 175 first lowered | 1322.906 | 150.271 |
| End | log ends 75 ms later (1322.98); report file empty, console froze | submission 9173 never completes; watchdog at 160.349 (`...140333-stderr.log:140`, `...140333-eden_log.txt` last line) |

The stuck submission of session 2 was already submitted when the 10 s count began, at 150.349 at the latest. The Z16 pipelines (150.368) and compute 185 (150.370) were built after that, so they are not in it. It can hold family B's S8Z24 task draws, the dispatch of compute 174 and the draws of mesh pipelines 175 and 176.

### Inferred

- Session 1's constant 5.3 s per frame from the first family B frame is what never-written ring entries with pool leftovers would give: the same oversized counts every frame. Session 2 started from a cleaner pool and ran family B without cost.
- In both sessions the end follows the first use of compute 174 and mesh 175 within 80 ms. Compute 174 reads the same `c3[0x100..0x10c]` parameters as family B's culling. If its output feeds that culling, its first run is also the first time whole task workgroups are culled, which is the unwritten-count path. That would make rank 1 the cause of both sessions. If not, rank 2 stands on its own. The saved logs cannot tell these apart: no draw or dispatch count after the eighth mesh draw is logged.
- "The hang reproduces on v2 alone: neither the second game nor the decay is the cause" (`PLAN.md`, the MKW row) is too strong. The second game explains the difference between the sessions, and no baseline run exists to call the stall `v2`-only.

## 6. Question 4: the fix set

The diffs are written against the `v2` worktree at `7e115e3` and apply in this order (checked by applying the series to a copy of the files; `fix-1` alone passes `git apply --check`). None is applied.

| # | Diff | Change | Switch |
|---|---|---|---|
| 1 | `fix-1-task-count-init.diff` | `emit_spirv_mesh.cpp`, `EmitMeshPrologue`: a task program stores zero to payload word 1, then a workgroup barrier, before the guest code runs. Port of the shader part of `8e87cf5a66` (author SethRamey; cherry-pick credit `-x`, the rest of that commit is Intel-specific and not needed) | `EDEN_NX2_TASK_COUNT_INIT=0` restores the old code |
| 2 | `fix-2-mesh-group-limit.diff` | Our own change. `TaskEpilogue`: the count goes through `OpUMin(count, 65535)`, the Vulkan minimum and RADV's value of `maxMeshWorkGroupCount[0]`. `vk_rasterizer.cpp`, mesh branch of `Draw`: a direct task/mesh draw with more than 65,535 groups is skipped and logged ("Task/mesh draw skipped: N groups from F") | `EDEN_NX2_MESH_GROUP_LIMIT=0` turns both off |
| 3 | `fix-3-radv-task-ring-zero.diff` | Optional, driver. `radv_device.c:1731`: `RADEON_FLAG_ZERO_VRAM` on `task_emu_bo`, as the publish ring has. Written against PS5_Mesa `7b59ef27`; in this repository it has to be carried as a `tools/patch-radv-*.py` step (`tools/build-radv-dependencies.sh:44-46`) and needs a RADV rebuild | none |

Notes:

- Fix 1 removes the stale read whatever the ring holds. Fix 3 only removes the pool leftovers, so it is not needed once fix 1 is in.
- The Eglantine pipeline cache stores guest code and SPIR-V is emitted again at each boot, so the shader changes and their switches take effect without a cache version bump (inferred from `shader_environment.cpp:283-345`; the driver's own caches are keyed by the SPIR-V).
- `v2` is now at cache version 32 (`be3a1de`): the console's version 31 file will not be read, and the next MKW boot builds all 191 pipelines at run time.
- Unchanged and still separate items of `PLAN.md` S2: the `UpdateIndexBuffer` half of 0056 and 0022.

Ring dump format (stderr, so it reaches `stderr.log` even when the eden log is not flushed):

```
NX2_DRAW_RING blocked_ms=1002 waited_tick=6959 gpu_tick=6958 recorded=812345
NX2_DRAW_RING tick=6959 mesh programs=<task>,<mesh>,<fragment> values=groups,instances,0,first,base_instance,0,0,0
NX2_DRAW_RING tick=6959 dispatch programs=<compute>,0,0 values=grid_x,grid_y,grid_z,block_x,block_y,block_z,0,0
NX2_DRAW_RING tick=6959 dispatch-indirect programs=<compute>,0,0 values=<x,y,z read from guest memory>,block_x,block_y,block_z,0,0
NX2_DRAW_RING tick=6959 draw-indirect programs=.. values=max_draws,stride,count (ffffffff: none),record word 0..4
NX2_DRAW_RING end small_direct_draws=412
```

Only entries of submissions the GPU has not completed are printed. The first tick above `gpu_tick` is the one the GPU is in. Direct draws with `count * instances` under 2^20 are counted, not listed. Indirect records are read from guest memory and can be older than what a GPU-written buffer holds.

### Safeguards today, and where they are set

- Stall limit: not in `headless/`. It is RADV's `RADV_PS5_STALL_NS`, 10 s, fixed at compile time (`mihawk-mesa-review/src/amd/vulkan/winsys/ps5/radv_ps5_winsys.c:86`, watchdog at `:91-121`). The loss reaches `vk_master_semaphore.cpp:118-128`, then the terminate hook at `headless/main.cpp:374-387`, then `Eden::Crash::Fail`. The driver honours finite wait timeouts (`radv_ps5_sync.c:144-155`), which is what the 1 s slices rely on. `headless/stall_watchdog.h` only reports a stalled game boot in development builds and is disarmed once the guest runs (`headless/main.cpp:1663`); `headless/stop_limit.h` is about a game that does not stop.
- Restart: `headless/crash_report.cpp:443-445` decides it (`restart`, stored in `leave`), `Restarter` at `:510-515` calls `eden_restart_app()` (`src/lifecycle.c:26`). Today only a crash within 60 s of a restart with no game started closes the app; there is no switch.

### The boot

One build: `v2` plus `fix-1`, `fix-2` and `diag-mkw`. Mario Kart World as the first game after opening the app, the owner at the console, kernel log (port 3232) recorded from before the launch, stop at the title screen for 5 minutes. `env.txt` (save the owner's file first and put it back afterwards):

```
EDEN_NX2_DRAW_RING=1
EDEN_NX2_STALL_MS=3000
EDEN_CRASH_NO_RESTART=1
EDEN_LOG_FILTER=*:Info Shader:Debug
EDEN_NX2_READBACK_DIAGNOSTICS=1
```

The last two lines are the environment of session 2, kept so the logs compare. Both fixes are on by default.

| Outcome | Meaning | Next |
|---|---|---|
| The title survives 5 minutes, no `NX2_DRAW_RING` line, no "Task/mesh draw skipped" line | the unwritten task count was the cause (rank 1) | proof by the reverse boot: the same build with `EDEN_NX2_TASK_COUNT_INIT=0` and `EDEN_NX2_MESH_GROUP_LIMIT=0` must stall near 40 s; the 3 s limit ends it and the ring shows family B's task draws in the stuck tick |
| It survives and "Task/mesh draw skipped: N groups" lines appear | the guest's own draw count is out of range: the data that count comes from is missing on `v2` (rank 3) | follow the logged program hash to its count source |
| `NX2_DRAW_RING` and `NX2_STALL` appear | rank 1 is not the cause, or not the only one. The entries of the first unfinished tick name it: a `dispatch` of `12c5e44ec761705b` with its grid, a `mesh` entry of `6a9f7874648dd6f6` with its group count, or family B entries with ordinary counts (then the wait is inside the driver's emulation) | one targeted change on that entry |

Why the fixes are on in this boot: the rank 1 defect is certain and has to go in anyway, every outcome names the next step, and no outcome needs a deliberate 10 s hang of the GPU. The alternative in `PLAN.md` S2 step 1 (the installed build with `EDEN_NX2_NO_MESH=1`) needs no build but cannot separate rank 1 from the mesh half of rank 2, and it says nothing about the compute dispatch if the stall stays.

Existing switches for a follow-up: `EDEN_NX2_NO_MESH=1` (`vk_rasterizer.cpp:293-298`), `EDEN_NX2_SKIP_VS=<address,...>` (`:678-693`) and `EDEN_NX2_REJECT=<address,...>` (`shader_environment.cpp:512-521`). The last two match program addresses, which moved by `0xc00000` between the two sessions, so they cannot be set in advance; a hash-based skip would be needed for that.

## 8. Limits of this analysis

- Nothing was compiled: the diffs were checked for applying cleanly and reviewed against the types they use, and the ring header was compiled and run on its own. A build may still ask for small corrections.
- Family B's group counts, the grid of compute 174 and the group count of mesh pipelines 175 and 176 are in no log.
- Whether compute 174 is accepted by the baseline's lowering was not determined (it uses `RED` and `SUST`).
- How session 1 ended (watchdog or crash) cannot be read from its files: the report is empty and stderr stops at the last 10 s window.
