# eglantineps5-port.md: what EglantinePS5 `main` changed outside the core after `v2`'s fork point, judged for `v2`. Writer: its triage agent (2026-11-10)

EglantinePS5 `origin/main` moved from the fork point `44d0d9d` (`horizon-ps5` `d1e57fb`) to `095df4e` (2026-11-10): 98 non-merge commits in 30 merged pull requests. This file covers everything that is not a core patch: `headless/`, the repo-root `src/` port runtime, `tools/`, `Makefile`, `sce_sys/`, `fixtures/`, `docs/`, plus the open pull requests and the unmerged branches. The core patches (`tools/eglantine-patches/0018` to `0071`) are judged one by one in [eglantineps5-main.md](eglantineps5-main.md); their verdicts are quoted here in brackets and not argued again.

Nothing here was built or run. Every measurement is EglantinePS5's own, from its pull requests and `docs/`, taken on its maintainer's console (a PS5 Pro, with Pro memory since #55 unless a row says otherwise). The owner's console is a base model (CFI-2114, firmware 13.60, 12,224 MiB pool).

## Method

- Scratch: `/Volumes/Hangar/ps5/scratch/triage-20261110/ps5-port/`. `repo/` is a clone of `horizon-ps5` without a checkout, with EglantinePS5's objects as alternates (`v2` is `origin/v2`, `b89bf69`). `prs/<n>.md` holds each pull request's text and comments (#46 to #98).
- **Applies to v2**: `git merge-tree --write-tree --merge-base=<commit>^ <tree> <commit>`, in EglantinePS5's merge order, each result tree feeding the next (`chain.txt`, final tree `dc97a13e`). A core patch counts as a file under `tools/eglantine-patches/` there, so the column only speaks for the non-core part. Result: 98 commits = 5 already in `v2` + 93 new, of which 87 apply cleanly in order. The real conflicts are seven small files (table at the end of section 1).
- **Anchors**: `v2`'s `tools/prepare-vulkan-port.py --report` passes on `v2`. EglantinePS5 `main`'s script, run against `v2`'s core without the new core patches, has 2 broken anchors, both from #57's commit `a74df7f` (part of #60): the `sw_blitter/blitter.cpp` write-back mark (`v2` has it indented inside a scope, from dj:b096fbea66) and the pipeline cache write in `PipelineCache::~PipelineCache()` (`v2` changed it with li:d1b7f69df7). Every new CMake anchor of `headless/CMakeLists.txt` and `headless/*.cmake` is found in `v2`'s core text (a static check, not a configure run).
- `v2`'s own port work that the rows collide with: rumble (`aa1faa2`), the 32 MiB gate on heap site reports (`bb480a5`), the shader cache check (`8f8e052`, `183b93f`), the nx2-core-check tests (`a137161`), #19's worker affinity (`c3de8e9`). `v2` never changed `src/`, the launcher (`headless/eglantineps5/`), `sce_sys/`, `fixtures/` or `tools/deps.json`, so changes there apply as written.

Verdicts as in [README.md](README.md): `port`, `in v2`, `adapt` (wanted, but it meets `v2`'s own work: the row names the files and which side wins), `measure`, `skip`.

## 2. Fastmem window (#49, #61/#73, #62, #63, #64)

The core side (0020, 0021) and the port commit list are in [eglantineps5-main.md](eglantineps5-main.md) (section "The fastmem window"). This section adds how it works and where it meets `v2`.

**How it works.** `Window64` in `src/host_memory.cpp` reserves a 2^38-byte arena for 64-bit games. It starts empty. A JIT memory access goes straight to `arena + guest address`; the first access to a place faults, and the handler (`headless/fastmem_handler.cpp`) aliases the guest's backing there and repeats the access:

- a whole 2 MiB region when the slot has its own block (`AliasGuestSlot`);
- otherwise 16 KiB pieces (`AliasGuestPage`). Each pieced region costs one CPU page table; new ones stop while fewer than 1,024 of the title's tables are free (`sceKernelGetPageTableStats`);
- a site the window cannot serve (guest address and backing disagree modulo 16 KiB, a refused piece) is demoted for the whole process to the page-table path, and the list of demoted sites is saved per title in `user/cache/jit/<title>.fastmem64-sites` (format `EF66`; the format is bumped whenever the rules change, so the first session after an update is a learning session);
- aliases are dropped under the slot lock before every promotion, return, scan fence and release (`src/guest_memory_service.inc`);
- the A64 range check goes to 2^38 even in Auto accuracy;
- an `EDEN_FASTMEM64` line in `heap.log` every 5 s counts faults and refusals.

**Switch and default.** `EDEN_FASTMEM64=1` in `env.txt`. Off by default on `origin/main` today; the maintainer keeps it opt-in "until it beats the defaults by more than run-to-run noise". `EDEN_FASTMEM64_STRICT_PIECES=1` restores the strict piece rule of before #64.

**Files outside the core.** `src/host_memory.cpp`, `src/fastmem.h`, `src/guest_memory_service.inc`, `src/memory_pages.cpp`, `headless/dynarmic/fastmem-callback.cmake` (new), `headless/dynarmic/shared-jit.cmake`, `headless/dynarmic/page_reuse_pass.inc`, `headless/CMakeLists.txt`, `headless/fastmem_handler.cpp`, `headless/graphics.cpp`, `headless/main.cpp`, `headless/memory_check.cpp` (`CheckWindow64` 20 cases, `CheckReadTrapAreas` 7 cases), `docs/FASTMEM64-WINDOW.md`. ### `v2`'s hang against those findings

`v2`'s two sessions (`/Volumes/Hangar/ps5/logs/boot/mkw-run2-live/`, `/Volumes/Hangar/ps5/logs/boot/mkw-freeze-1322/`) end the same way: the game loads, the menus run at 60 fps, then within seconds of entering a scene the GPU stops (`radv/ps5: the GPU has not reached submission 9173 (at 9172) in 10 s`, `VK_ERROR_DEVICE_LOST` at 160.35 s in run 2; in the first session the console froze).

What the logs rule out: the pool had 4,390 MiB free in its largest block; no "Too many open files"; no "instruction limit"; no draw skipped for its size; and `v2` has no transfer split, packing or trim. So none of EglantinePS5's fixed causes is `v2`'s hang. The two 16384x16384 unbacked sparse images and the 16 `Unmapped Device ReadBlock` lines are baseline behaviour (`EDEN_NX2_SPARSE_UNBACKED=1` is set by `headless/main.cpp` in both trees, and #76 shows the same reads upstream).

Candidates, most likely first. All are inferences from the logs and the code; none was run.

1. **`v2`'s own tessellation lowering.** `a69af6d` lowers tessellation programs natively (before, `shader_environment.cpp` left every program except vertex B, geometry, pixel and mesh slots to the old path) and `756a323` builds their pipelines. EglantinePS5 `main` has no tessellation lowering in any patch, so it never draws these pipelines. In both sessions the hang follows newly built tessellation pipelines by seconds: 5 "Patch topology not used with tessellation, using patch list" lines at 150.368 s in run 2 (the driver reports the stall 10 s later; 7 earlier lines at 110.0 s are the pipeline cache preload at session start, built but not yet drawn), a tessellation pipeline at 1254.09 s and 5 more at 1256.69 s in the first session (GPU stopped at 1256.7 s). mihawk's RADV runs tessellation with a geometry shader that amplifies past one NGG subgroup, or with transform feedback, as compute (`radv_gs_compute`), which is the driver path #77's `patch-radv-gs-compute.py` had to harden. Test: `EDEN_NX2_REJECT=<the tessellation programs' addresses>` in `env.txt` (the switch exists in `shader_environment.cpp`); a switch that skips tessellation pipelines as a whole does not exist yet and would need a build.
2. **Task and mesh draws from programs the baseline rejected.** The baseline issues task and mesh draws (patch 0004, `DrawMeshTasksEXT`), and upstream's runs on the same Mesa pin did not hang on them, so the draws alone are not the cause. But `v2`'s batch 4 register shadowing lowers programs the baseline rejected, and upstream's equivalent (#96) switched on Ocarina of Time task draws that read records nobody wrote (#98). #95's authors report that on a newer PS5_Mesa (`f5610fe27`, not in our checkout) every task and mesh draw hung the GPU in Ocarina of Time and in Mario Kart World. Run 2 logs 8 `task mesh draw groups=1` lines at 145.235 s, 5 s before the hang. Test: `EDEN_NX2_NO_MESH=1` in `env.txt` (already in `v2`).
3. **A newly lowered compute program.** At 150.370 s run 2 lowers a 256,144-byte, 28,102-instruction native program and builds its compute pipeline in 118.5 ms, in the same frame as the tessellation pipelines. A compute dispatch that never finishes gives the same driver message. Test: `EDEN_NX2_REJECT` with that program's address.
4. **A dropped draw in the driver's geometry-as-compute passes.** The fault `patch-radv-gs-compute.py` fixes (null buffers for a dropped draw). It is a GPU fault upstream, not a stall, so it fits less well, but it is the one driver-side fix `v2` lacks that touches the path of candidate 1. Cost: one RADV rebuild.
5. **A draw that runs past the driver's 10 s limit.** The class 0056 fixes. `v2`'s 2^24 guard covers vertex and index counts and logged nothing; instance counts and task workgroup counts are not capped, so it is not fully excluded.

Order of work this suggests: `EDEN_NX2_NO_MESH=1` and `EDEN_NX2_REJECT` are `env.txt` experiments on the installed build (one boot each, with someone at the console because the first session froze it); the RADV GS-compute sink and #68 go into the next build; the memory stack (#69, #90) only after the hang is found, since packing was itself a hang cause upstream and would blur the bisect. Once past the hang, a base console needs that stack to load a race at all.
